# Complete CAD robot projects

Open **CAD → Examples** and choose a robot. The main robot cards in
**Shapes → Robots** open the same complete projects; manufacturing parts and
fit coupons remain ordinary insertable shapes. CAD is enabled in Settings.

Each choice uses Brickwright’s shared SB3 loader and restores the assembly,
editable green-flag Blocks, pseudocode source, Arduino Uno circuit, motor-driver
wiring, CAD actuator bindings, and live Widgets together. Confirm replacement
only after saving your current project. Cancelling preserves it. Loading does
not start the program.

After opening, the **Controls** drawer appears. Press **Run**, then move its
sliders. These are the same Widgets that the program reads. **Program → Edit
program** opens the editable program; the Circuit tab shows its actual wiring.
The normal Widgets editor edits these controls. Stop/Reset use the shared
simulation lifecycle. Saving an SB3 retains all these sections.

## Models and behavior

- Scout: left/right TT drive, encoder circuit, two speed controls; starts at 30%.
- Trident: two TT drives and steering servo; centered controls on load.
- Atlas: two wheel drives, a linear lift and fork-tilt servo.
- Mantis: three servo joint controls.
- Cyclone: two linear stages and a sweeper servo.
- Helios: turret and catapult servo controls.

The 22 bundles are generated by `scripts/generate-cad-robot-projects.mjs`
from the committed CAD factory documents. They are not geometry-only presets.
Real controller reporters and device-control blocks connect the program to
Board’s electrical simulation; the coupled mechanical solver owns joint poses.
There are no direct CAD pose assignments in the example programs. Outputs are
updated when a Widget changes, rather than rewriting unchanged pins every tick.

Circuits use nominal 6 V batteries, Uno pin wiring and L293D bridge models.
Continuous TT drives use output-shaft-equivalent constants; linear stages use
nominal bare-rotor constants and an ideal 8 mm/revolution transmission.
These parameters are explicit educational assumptions, not calibrated product
measurements. Positional servos are torque-limited ideal actuators; their
power draw is not modeled. Widgets are simulation inputs, not hardware inputs.
A firmware deployment needs an appropriate hardware input/control program.

## Qualification limits

Browser checks exercise the real GUI, project loader, VM, Widgets, Board and
mechanical worker. Scout, Atlas, Mantis, Cyclone and Helios have passed one-second
simulation checks with every mapped actuator moving and Stop/Reset working.
They do not certify walking gait, sorting success, catapult accuracy or
manufacturing readiness. Trident currently exceeds the bounded simulation time
budget with its detailed colliders; its project remains inspectable and editable,
and the UI labels its simulation experimental.
Solver limits, collision rules and time budgets remain unchanged.

See `docs/receipts/2026-11-16-cad-robot-projects.json` for tested source and
native build details. No GitHub Actions are used for this delivery.

The earlier shipped app embedded stale SB3 files from the GUI static mirror.
Its Atlas/Cyclone winding constants and uncached output-writing program were

inputs, and the final SDK/app verifier also checks all six SB3 content hashes

nonzero preset commands, and unchanged controls do not rewrite their outputs.
Two DC motors share the two channels of each driver. These real-time examples

and loose-object contacts remain active. World settings exposes the policy, and
older saved documents keep their prior choice. Internal clearance checking is
a separate, more expensive mode. No solver guard or geometry tolerance was raised.

## Sustained real-time target

The MacBook browser target for Scout and Atlas is at least 1× sustained
simulated time. Measure it between the first and last positive-time frames
reported by the coupled session. The 200 Hz electrical-to-mechanical feedback
loop gives every complete substep a 5 ms wall-clock budget.

| Project | Chrome baseline | Mean mechanical round trip | Mean electrical advance |
| --- | ---: | ---: | ---: |
| Scout | 0.15× | 29.2 ms | 3.0 ms |
| Atlas | 0.18× | 22.2 ms | 4.0 ms |

Set `PROOF_PHASES=1 PROOF_MIN_RTF=1` when running
`scripts/verify-cad-robot-projects.mjs` to record the phases and make the
real-time target a test assertion. `PROOF_REPEAT=1` also checks a second
Run after Stop/Reset with the same design.

The CAD worker releases the active Jolt world on Stop and retains one
qualified preparation for an unchanged design. The next Run creates a fresh
world from those immutable colliders. An edit discards the cached preparation.
This addresses restart latency. Sustained contact solving and cold startup
remain open.

A diagnostic Scout run with continuous collision detection disabled dropped
the mean native step from 19.3 ms to 6.4 ms. The latter still exceeded the 5 ms
combined budget before the circuit solve, and drive motion changed. The
shipped path retains continuous collision detection.

The pinned Jolt package also provides an optional SIMD build. The browser
worker selects it after a Wasm feature check and falls back to the scalar
build if it cannot load. The fixed timestep and the collision settings are
shared across both builds.

| Project | Sustained with SIMD | Mean mechanical round trip | First / repeat worker startup |
| --- | ---: | ---: | ---: |
| Scout | 0.249× | 18.2 ms | 11.39 / 0.92 s |
| Atlas | 0.220× | 18.1 ms | 8.50 / 0.63 s |

These are Chrome samples under varying MacBook load. A separate paired

The strict 1× check still fails for both projects.

Quasar completed the full cycle with SIMD and with the scalar fallback

### Batch circuit feedback at each mechanical step

Scout publishes two shaft readings and Atlas publishes three. Both now
apply all readings from one 5 ms step before solving the circuit. Older
Board packages still accept the individual readings. Input validation
completes before any shaft changes.

MacBook Chrome A/B with the same build and default controls:

| Project | Mean shaft-feedback time per step, individual → batch | Sustained rate, individual → batch |
| --- | ---: | ---: |
| Scout | 0.211 → 0.149 ms | 0.616× → 0.638× |
| Atlas | 0.269 → 0.170 ms | 0.624× → 0.551× |

Use `PROOF_PHASES=1 PROOF_LEGACY_SHAFTS=1` to force individual feedback for
comparison. The paired direct-Board benchmark used the same project circuits
and 900 steps per run. It measured two or three feedback solves per step
with individual updates, and one with batching. Accumulated motor impulses
matched exactly in that benchmark. The full Atlas run did not show a
sustained gain, and both strict 1× checks remain open. Mechanical round
trips in the batched browser runs averaged 7.17 ms for Scout and 7.31 ms
for Atlas.

We also qualified a smaller Scout wheel compound against the full source
mesh. It reduced the compound from 507 to 385 hulls per wheel and made
preparation faster in one paired run. Native stepping showed no reliable
gain, and the Scout motion qualification did not pass. The released
wheel assets retain their existing candidates.

On the published MacBook build, a reverse-order Atlas pair measured
0.653× batched and 0.417× individual. Shaft feedback averaged 0.151 ms
batched and 0.357 ms individual. Mechanical round-trip time varied
between the runs, so these pairs establish a feedback-stage reduction
with no reproducible end-to-end gain for Atlas.

### Reuse actuator geometry and impulse buffers

Each CAD world now caches the authored axis and, for sliders, the point
where force is applied. It transforms them with the current body pose
on every tick. Hinge impulses only need the axis. Jolt impulse and
position vectors are reused within the world and released on disposal.

An alternating mixed hinge-and-slider CPU test applied 100,000 impulses
per trial. The previous path used 13.1–14.4 µs per impulse, and the new
path used 7.1–8.7 µs, with identical resulting velocities. This measures
actuator preparation and application only. The native physics step
still determines whether the models can reach 1×.

A separate collision-filter experiment changed the Scout motion trace.
The actuator change retains the original collision filters.

Using the shipped Scout and Atlas SB3 models, the chassis poses and all
actuated joint readings matched the comparison build exactly through 100
steps for each model, including reversal and Atlas slider impulses.

The separately authored Scout clearance test assumes two runtime
separation proofs. Its original setup and the updated solver both
reported one, with equal poses and joint angles in a direct replay of
the test inputs. The known assertion is separate from the actuator
change. The fixed-assembly ground and loose-contact case passed when
rerun with time for the loaded Mac to finish.
