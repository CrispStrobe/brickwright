Status: **active plan, lane open**. Created 2026-09-05 by session `lego-ac`
(`Claude-Session: https://claude.ai/code/session_01L3xy8YZKHGfHAkysBEREXG`).
Owner of record for the truth lane (T1, T2) and the ASM reader (L1): lego-ac.
Every other task is unclaimed until a row in `LANES.md` says otherwise.

The product question this answers: *write in any language the Code tab offers,
run it on any chip the Circuit Designer or the device picker offers, in the
simulator and on real silicon.* Today that is partly true, partly false, and
nowhere written down in a form the GUI and the docs both read. This plan makes
one table the source of truth, shows it to the user, derives the docs from it,
and then lists what closes each cell that is still open.

## 1. Decisions (made — do not re-litigate in tasks)

### D1. A cell has two halves, and each half is a fact, not a verdict

For a language **L** and a device **D**, the cell records:

- **native** — L itself runs on D. The artefact is L's own program (a `.py`
  for MicroPython, a `.bas` typed into a BASIC ROM, a `.hex` from a C or ASM
  toolchain). Sub-facts: which toolchain, where it runs (`local` in the
  browser, `hosted` on stc-compiler, or `none` because the chip runs the
  language directly), and whether that artefact reaches the simulator, real
  silicon, or both.
- **lowered** — L is read into the dialect AST and re-emitted as something D
  runs natively. The learner's text does not run; its meaning does. Sub-facts:
  the reader used, the emitter used, and the native cell it lands in.

A cell is therefore one of **native**, **lowered**, or **both**. There is no
"refused" cell. Where a native half is physically impossible, the cell says
`native: null` **with a reason** (`ram`, `flash`, `no-port`, `no-emulator`,
`licence`) and the lowered half carries the load. "Physically impossible" is a
strong claim and every use of it in the table cites the number it rests on.

### D2. The table is data in the code, gated against the code

`overlay/scratch-gui/src/lib/bw-matrix/capabilities.js` is a frozen, versioned
data module. It is hand-authored — some facts (the hosted service's target
list) do not live in this repository — but every fact that *does* live here is
cross-checked by a test that reads the real source:

| fact in the table | checked against |
| --- | --- |
| device ids, groups, `compile`, `emulator` | `DEVICE_GROUPS`, derived beside `DEVICES`; exact transform + rendered UI contracts |
| silicon transport per device | `flashFamily()` and the `flasher.js` exports |
| local vs hosted assembler | `LOCAL_ASM_TARGETS` in `bw-asm/assemble-route.js` |
| local vs hosted C compiler | `LOCAL_TARGETS` in `sdcc-wasm/compiler.js` and `smallerc-wasm/compiler.js` |
| which cores `generateC` emits for | the `_core` selection in `sb3-creator.js` |
| which languages have a reader | the `sb3-creator-*.js` reader modules |
| hosted compile/assemble targets | `docs/generated/hosted-targets.json`, regenerated by `scripts/gen-hosted-targets.mjs` from a stc-compiler checkout (pinned at `79df4b6d`; the derived facts matched the hand read exactly, so the snapshot was accurate) |

A table row that the source contradicts fails the build by name. A table row
that nothing checks is marked `evidence: 'declared'` and rendered with that
label — the reader can see which facts are proven and which are only stated.

### D3. GUI and docs are both derived, never hand-maintained

Two GUI surfaces and one document read the same module:

- **Overall matrix** — a "What runs where?" view reachable from the Code tab's
  device dropdown: languages down, devices across, each cell native/lowered/
  both, with sim and silicon marks.
- **Contextual badge** — beside ▶ Run and ⬇ Deploy, for the *chosen* language
  and device: `native · sim + silicon`, `lowered via C · sim only`, or the
  reason nothing is available. The buttons' enabled state comes from the same
  lookup, so the badge cannot say one thing and the button do another.
- **`docs/generated/LANGUAGE-DEVICE-MATRIX.md`** — generated by
  `scripts/gen-language-device-matrix.mjs`, with `--check` wired into the build
  like the other generators. `docs/CHOOSING-HARDWARE.md` and
  `docs/device-matrix.md` link to it instead of carrying their own tables.

### D4. Native closures are preferred where a permissive runtime exists

Where a chip can run a language natively with a permissively licensed runtime,
we add the native half even though the lowered half already works, because a
learner who wrote Python and sees Python on the board learns something the
lowered path hides. Licences that qualify: MIT, BSD, Apache-2.0, zlib,
MPL-2.0 (file-level). GPL toolchains stay hosted, as they are today.

### D5. Peripheral verbs are a second table, joined to this one

Which parts a program can drive (`lcd print`, `oled pixel`, `set servo`) is
per part × per family, not per language × device, and is owned by the
part-profile lane (§3, Lane P). The matrix cell links to it: a lowered cell
that lands in C on the 8051 inherits the 8051 C driver set. The two tables
are joined by family id and nothing else.

## Code when a machine is selected

The Code language row and both language menus use the capability table for
native runtime and deploy reach. Pseudocode remains available for project
conversion. Keep lowerings and other incomplete routes documented in the full
matrix. Returning to Scratch stage restores the general-purpose language tabs
and any available authored drafts. Keep machine-specific BASIC profiles explicit
so Run uses the selected interpreter.

PicoBB, PiccoloBASIC, and [Stefan’s BASIC](https://github.com/slviajero/tinybasic)
each use pinned media-lab UART firmware. Code waits for each interpreter prompt
before sending the next line, and each profile retains its own draft.
PiccoloBASIC uses unnumbered source and labels. Stefan’s BASIC uses line numbers
for jumps and accepts `INPUT` in Controller. Blocks conversion is available
for PicoBB. The Pico BASIC actions in Code download the selected BOOTSEL
firmware and can replace the running interpreter's in-memory listing using a
3.3 V USB-to-UART adapter. Controller stays connected for input and Ctrl+C.
The first connection waits for the selected firmware banner and prompt, so
reset the Pico after choosing the adapter. The BOOTSEL image contains the
interpreter. All three Pico BASIC profiles provide 128 KiB of LittleFS for
named files. PicoBB starts from a preformatted empty filesystem.
Use `SAVE "demo.bas"` and `LOAD "demo.bas"` in Controller. Stefan’s BASIC
lists the files with `CATALOG`. PiccoloBASIC uses `FILES`. Its UART build
formats erased storage on the first file command and preserves a nonblank
partition that it cannot mount.
A simulated rerun preserves that partition. Project files and project history
carry the filesystem data, keyed to the exact firmware and partition layout.
Reopen the project or restore its autosave after restarting Brickwright.

The browser test uses a scripted serial adapter. The host protocol proof drives
the three pinned UF2s in the RP2040 emulator. Physical UART and native desktop
qualification remain open.

**N3d. The Pico sim's NODE-ORACLE transport did not drain the device CDC RX buffer — a large program truncated
in silence. CLOSED 2026-09-07** (found on P3 part 1). A physical Pico empties its USB-CDC host→device FIFO by
EXECUTING while the host writes; the emulated device only advances when something drives it. `pico-repl.js`'s
`writeChunked` drains between 64-byte packets IFF the transport implements `drain()` — and only ONE of the two
transports did: the shipped BROWSER transport (`pico-sim-run.js`) has `drain()` (it yields an rAF frame so the
pump consumes the packet); the node ORACLE transport (`scripts/probe-pico-micropython.mjs`, a test/probe seam,
NOT shipped) did not. Without a drain every packet piles into the 512-byte `txFIFO` with no stepping between,
and past 512 `FIFO.push` DROPS SILENTLY (an `if (used < length)` guard, no signal), so the raw-REPL never sees
the whole program and its OK never arrives.

The earlier sentence here — "the shipped N3c very likely fails silently on any program past one buffer" — was a
PREDICTION, and measurement REFUTED it. Running a ~1.2 KB generated program through both seams showed the
shipped browser path drains and runs it fine; only the node oracle, which lacked `drain()`, timed out. So the
defect was in the oracle, not the shipped browser N3c, and the fix is one method on the node transport with
`pico-repl.js` and every shipped file untouched — the refutation, not the original prediction, is the finding.
Done (worker, `scripts/probe-pico-micropython.mjs` + `test/pico-sim-transport-drain.test.mjs`): (1) measured —
the node oracle failed on 1235 B and the txFIFO caps at exactly `TX_FIFO_SIZE` = 512 (overshoot dropped without
a signal); (2) `drain()` added to the node transport — it pumps the machine until `txFIFO` is empty (the drain
observable in the test), the threshold read from rp2040js's own `TX_FIFO_SIZE`; (3) a >buffer program now runs
live through the node oracle, green ONLY with the drain, and P3's differential runs the FULL `.py` on the same
branch; (4) mutation: hide `drain()` (exactly the pre-fix transport) and the same program times out naming the
OK-wait. Raw-paste mode upstream (the `pico-repl.js` protocol) is a follow-on only if a future program outgrows
the chunked-drain path.

at our current pin. The one-byte cause: with the version byte zero, pico-sdk's shim-table initialiser
took its "old bootrom" leg and left 31 of 32 double-precision operator pointers null; the first GPIO
call went through a null pointer into the ROM's zeros.

first half already states: a compiled-C oracle must not reach the hardware through OUR ROM, or the
oracle and the thing under test share a failure mode. That holds whether or not the ROM works. It is a
**different** reason from "the bootrom would hang", and the two exclude different Door 2 designs — and
because the wall is gone **at our pin**, a Door 2 that boots a compiled image THROUGH the bootrom is
genuinely open, not blocked (subject to the flash-entry limit below, which is a separate question).

**One limit, kept visible — and now narrowed on one half, not closed.** `--blink` sends a REPL line
and watches `gpio[25]`; it does NOT load a program, so it drives the hardware through the same
run-live seam already measured, not through a distinct loaded-image entry. **Narrowed 2026-09-17**
(bw-board `b8faec5`, verified 19 commits ahead of our pin `76877a2` — still upstream, not in lite's
tree, and a DIFFERENT commit from the version-byte fix `64354e8`, which IS pinned): `test/rp2040-bootrom-guest-abi.test.mjs` loads a 24-halfword Thumb
program into SRAM that performs the documented ROM sequence itself — reads the u16 at `0x16`, reads
`rom_table_lookup` at `0x18`, `blx`-es it with the `'SF'` code, loads an entry and `blx`-es that —
reaches every fixed-point conversion and agrees with `Math.fround`; a mutation asking for `'XF'`
misses the lookup and the guest publishes 0 through the null slide, so the lookup is load-bearing.
That closes *can a loaded program use this ROM's ABI at all* — **yes, from SRAM through the
documented lookup**. It does NOT close *a compiled C image boots through the bootrom*: that guest is
hand-written Thumb entered at RAM_START, not an image entering via the flash boot path, and this
ROM's reset vector still goes to a spin. So the **flash-entry half is still UNMEASURED** — if Door 2
ever stops jumping past the bootrom and boots an image the flash way, that path has no evidence
behind it and still wants its own lane.

## 4. Milestones

**M1 — Truth (T1–T5).** The GUI shows what runs where, the docs are generated
from the same module, and the three known contradictions are fixed. *Exit:*
`verify:matrix-ui` and `gen:matrix:check` green in CI.

**M2 — Cheap native closures (N1, N2, N4, N7, L2).** Z80 and 8086 gain C;
ARM gains ASM; the micro:bit gains C; the Pico's C path is reachable. *Exit:*
each cell's DoD green; the matrix regenerated.

**M3 — Simulator parity (N3).** Python on the Pico runs in the simulator as
it does on silicon. *Exit:* `verify:pico-micropython` green.

**M4 — The last language gap (L1) and reader truth (L3).** ASM reads back
with counted refusals. *Exit:* L1 DoD green.

**M5 — Investigations decided (N5, N6, N8, L4).** Each ends in a doc with a
measurement and either a build task or a `native: null` reason the table
cites.

**M6 — Peripherals (Lane P)**, sequenced after M1 so the part table joins a
matrix that already exists.

Parallelism: T1 first (everything renders from its schema). Then N1, N2, N3
are independent of each other and of T3/T4, and are the first wave for
delegated agents — N2 first because it is now measurement plus wiring. L1 is the long pole and stays with the owner.

## 5. Non-goals — write refusals, not scope creep

- A Python or JavaScript interpreter on the 8051, AVR, STM32F030, 6502, Z80 or
  8086. The table says `native: null` with the RAM or port reason; lowered
  covers the cell.
- A SAMD51 instruction emulator. Upstream Rust work in labwired; not here.
- Arduino library compatibility in general. Known APIs map to verbs (P4);
  the rest is a named refusal.
- General decompilation. L1 lifts known shapes and says what it did not lift.

## 6. Risks and tripwires

| risk | tripwire | response |
| --- | --- | --- |
| The table drifts from the code | T2 gates, mutation-proven | a red build, by name |
| Hosted service changes under us | nightly snapshot diff (T2) | report, then bump the snapshot deliberately |
| Machine load kills long test runs | `scripts/check-system-load.mjs` | single-file tests; never a full suite on a loaded box |
| A "physically impossible" claim is wrong | every `null` reason cites a number | fix the number, the cell opens |
| Two sessions close the same cell | LANES rows per task id | the row is the lock |
| A check measures a MODEL of the thing (trace, log, cache, proxy, summary), and the defect is silent in the model by construction | the tell: a NEGATIVE result from an instrument built by the same work that would have produced the positive (LANES 13, lego-a4). Three instances on 2026-09-05: `busTrace` vs the `read()` callback (a bare peek is silent in the trace, audible on the bus — lite's `i8086-performance-regressions` caught upstream `71cc1ca` by counting callbacks), run-duration vs job-duration, a vendor guard comparing the incoming file when the question was the old pin | count the thing itself; a fetch-path or bus assertion counts callbacks, never trace rows; a memory dump is a model only while nothing else writes it (an interrupt handler always does) |
| Evidence for a sim cell rests on our own programs | third-party code that predates the emulator: ELKS 0.9.1 boots on the 8086 tier and mounts its root filesystem (bw-board `824d301`, banner at 1.31M instructions, root at 2.36M; BIOS ROM, uPD765, 8237 and 8259 driven together) — tier 2a in spirit, `needs: ['elks-image']`, `ciAvailable: false` (GPL-2, never vendored), so recorded, not standing. The number under the claim: that boot completed with ONE wrong two-sector INT 13h read in 230 (bw-board `915997c`/`dd477a9`, E6.8.8b). Cause identified and reproduced: `rom/bios.asm`'s diskette parameter table declares EOT=9 (a 360K table) while the media are 1.44M (18 sectors/track), so a multi-sector read crossing sector 9 switches heads early — the uPD765 and 8237 models did exactly what they were told, and a device unit test would pass. The MINIX image did not boot for the same reason. FIXED upstream `8064729` (lego-a4): the driver reads the diskette parameter table THROUGH the INT 1Eh vector (making the ROM's documented hook contract true), three tables (360K/1.2M/1.44M), one VERIFY-mode media probe (18, then 15, then 9) after the last refusal in `fd_xfer` — its placement decided by the 64K-boundary test that pins "a refusal costs nothing to undo" — and AH=08h answers the detected geometry. Measured: MINIX 121 reads/21 wrong → 127/0; FAT 230/1 → 230/0; the three tests that pinned 360K behaviour pass untouched; the 1.2M branch is DECLARED, NOT MEASURED (no image). ELKS 0.9.1 now boots from the MINIX image and probes 80/2/18 correctly but does NOT mount root (its FAT driver is tried on a MINIX filesystem: "FAT: Unsupported format"). Still open: CMOS drive type, equipment word, 3F7h data rate (ELKS's df driver reports 360K) | DONE: the 8086 `sim` engine's `needs` carries `elks-image` (renders **recorded**, since GPL-2 keeps it out of bw-board's CI) beside the standing `8086-vectors`; the geometry contract closed upstream in `8064729` and ships in lite's ROM since the pin to `9a770c8`. Tripwires (lego-a4): ask the cheap question first — are the bytes being executed the bytes on the disk; and a subset of a suite chosen by the person changing the behaviour cannot disagree with them — nor can a pattern read off the cases that happened to fail ("odd start sectors" was five odd samples; the predicate was "reaches sector 9", bw-board `5c778ba`) — both are the sample answering instead of the thing, so run the tests that PIN the behaviour, and test the pattern against the cases that passed, before writing a general claim; and a test that pins a COST ("the 8237 was never programmed, so the refusal costs nothing to undo") catches side effects no functional assertion would — keep such tests when they are inconvenient |
